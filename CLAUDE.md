# Recipe Box — Claude Code Context

> Project-specific guidance. Security, token efficiency, and writing rules are in the vault-level `CLAUDE.md`. Full plan: `docs/SPEC.md`.

## Quick start

```bash
# Backend (FastAPI) — ⚠ port 8002 (mtg-web owns 8001)
cd backend && uvicorn app.main:app --port 8002
# Run WITHOUT --reload on Windows — reload leaves zombie workers holding the port

# Frontend (React/Vite)
cd frontend && npm run dev   # http://localhost:5173 — .env VITE_API_BASE must point at 8002

# Tests — stdlib runners on both sides, no dependency, no build step
cd frontend && npm test
cd backend && python -m unittest discover -s tests
```

**Tests cover the pure libs, which is where a silent wrong answer lives.**
`src/lib/*.test.js` runs under `node --test` because everything in `lib/` is
plain ESM with no DOM: no vitest, no jsdom, nothing in `devDependencies`, and the
files never enter the bundle since nothing imports them. `ingredients.test.js` is
the important one — parsing, merging and aisle grouping fail by producing a
plausible list that is quietly short an ingredient, and the place that gets
noticed is a shop. `tags.test.js` ends by parsing `ALLOWED_TAGS` out of
`backend/app/ai.py` and comparing it to `TAG_VOCABULARY`, which is the only thing
actually enforcing the "keep the two lists in step" rule below. `dates.test.js`
walks a full year through `toISODate`/`fromISODate` rather than spot-checking,
because the naive `new Date(iso)` passes a spot check in UTC and fails everywhere
else — that failure moves an evening meal to the day before.

**CORS has three layers and they are not interchangeable** (`backend/app/config.py`). Named origins come from `RECIPE_CORS_ORIGINS`, comma-separated, and that variable is the *only* thing letting the production frontend call the API — empty it and the live site starts failing every request. The localhost pair is added only when `VERCEL_ENV` is unset, so a deployment no longer ships an allow-list trusting a laptop. Preview hostnames change per branch and so are matched by `DEFAULT_PREVIEW_ORIGIN_REGEX`, which is deliberately qualified by the Vercel account slug and anchored: unanchored, `…vercel.app.evil.com` matches. Without that regex no preview deployment can reach the API at all, and every import fails as "Failed to fetch". `backend/tests/test_cors.py` pins all of it, including what must stay refused.

## Architecture

- **Frontend:** React 19 + Vite + vite-plugin-pwa, JSX (not TS) to match mtg-web conventions. State centralized in `App.jsx`, props down, no state library. Recipes go through the store abstraction in `src/lib/store.js` — localStorage `recipebox:recipes` when signed out, Supabase `recipes` table when signed in. On sign-in, local captures upload once and the local key is cleared (cloud becomes source of truth).
- **Backend:** single Vercel Python Function from `app/main.py`, deployed at **recipe-box-api-sage.vercel.app** (project `recipe-box-api`, FastAPI framework preset, root dir `backend`, zero-config — no vercel.json; fluid compute default 300s maxDuration). `app/extract.py` holds the scraping pipeline. **A new dependency goes in `backend/pyproject.toml` as well as `backend/requirements.txt`** — Vercel installs from `pyproject.toml`, so a package listed only in `requirements.txt` is absent in production while every local check passes. Phase 7 shipped Pillow that way and took the entire API down: `images.py` imports Pillow at module scope, `main.py` imported `images` at module scope, so the ASGI app never constructed and *every* route returned `FUNCTION_INVOCATION_FAILED`, extraction included. Both halves of that are now guarded — the lists must match, and `main.py` imports `auth`/`images` inside their handlers so a missing dependency costs one endpoint instead of the API. `/api/health` reports `images` for exactly this, since mirroring fails silently by design and otherwise a missing package is indistinguishable from a photo that wouldn't download. Dotdash Meredith sites (AllRecipes, Serious Eats) block Vercel IPs — extraction fails there by design of their bot protection.
- **Frontend deploy:** **recipe-box-coral.vercel.app** (project `recipe-box`, Vite preset, root dir `frontend`). Env vars `VITE_API_BASE`/`VITE_SUPABASE_URL`/`VITE_SUPABASE_ANON_KEY` are build-time — changing them requires a redeploy. Both projects build on every push to `main` (github.com/dreandyyttv-bot/recipe-box).
- **A branch preview cannot test anything that touches the API. Don't try.** `VITE_API_BASE` is baked in at build time from the project's env vars, so a preview frontend calls the *production* API, not the API's preview of the same branch — a backend change is never what a preview is exercising. Worse, until a CORS change is live on production the preview's own origin isn't on the allow-list, so import, paste and photo mirroring all fail as **"Failed to fetch"** (the fetch promise rejecting, i.e. no response reached JS at all — a real extraction failure would surface as "Could not find a recipe at that URL"). The API preview does exist, but Vercel deployment protection answers it with a 302 and nothing routes to it anyway. **Test backend behaviour locally**, where localhost is allowed. What previews *are* good for: anything Supabase-backed, since Supabase accepts any origin bearing the anon key — sign-in, sync, the editor, planner and shopping all work, and the preview origin has its own empty localStorage, which makes it the cleanest way to test the signed-out-then-sign-in migration without disturbing the production origin. Note that it writes to the real database while doing so.
- **Storage:** Supabase, dedicated project (NOT shared with mtg-web) — schema in `supabase/schema.sql`, RLS per user, magic-link auth in `src/components/Account.jsx`, client in `src/lib/supabase.js`. Env vars unset = local-only mode (no auth UI rendered).
- **AI:** `claude-haiku-4-5` structures captions and pasted text (`app/ai.py`). Uses **structured outputs** (`output_config.format` + `RECIPE_SCHEMA`) — the model cannot return prose, so never add fence-stripping or `json.loads` fallbacks around it. Schema rules: `additionalProperties: false` on every object, `required` must list every property, and no `minimum`/`maxLength`-style constraints. `enum` *is* in the supported subset and is what pins `tags` to `ALLOWED_TAGS`. Spend is capped monthly via `app/usage.py` → Supabase `ai_usage_events`; both usage calls fail open so a Supabase outage never blocks an import.
- **Social import:** `app/social.py` — TikTok oEmbed (its `title` field is the caption), Instagram/other via og: tags. **Instagram serves the caption wrapped in page chrome and both fields carry a different wrapper** — `og:title` is `Name on Instagram: "caption"`, `og:description` is `25K likes, 59 comments - handle on date: "caption"`. `unwrap_caption` strips either; never feed those fields to the model raw. Doing so put engagement counts in the recipe text, which is enough for the model to call the post a social blurb rather than a recipe, and the link-card fallback then saved the `og:title` blob as the recipe's *name*. Because `og:description` is the field Instagram truncates, the longer of the two unwrapped fields wins, and the name comes from the caption's first line (the dish) rather than the account. No caption or no recipe in it means a **link card**, not an error. Captions are untrusted: they stay wrapped in `<user_input>` tags with injection defense in the system prompt.

## Conventions

- **The picture is read only when the caption fails** (`_read_post_image` in `extract.py`, phase 8). A caption that parses never triggers a vision call, so an ordinary import still costs one model call; an import that was going to be a link card costs two. Every failure path returns `None` and falls through to the link card, so this can never turn a working import into an error. Images are prepared by `image_for_vision` (`images.py`), which caps the **long edge** at 1568px and the **area** at 1.15 MP — the API downscales past either, and they are separate limits (a 1150×1568 portrait clears the edge and is still 1.8 MP). Text and image structuring share `_structure` in `ai.py`; don't add a second model-call path, that's where the budget check lives. Text rendered into an image is as untrusted as a caption — the system prompt covers both.
- Ingredients always keep the `raw` string; parsed qty/unit/item are best-effort (shopping list depends on them, phase 4b). Note `extract.py` sets all three to `null` on the JSON-LD path, so only AI-structured recipes have them.
- **The AI normalizes every recipe to English, `raw` lines included** (the language rule in `SYSTEM`, `app/ai.py`). TikTok's oEmbed returns the creator's original caption and never the auto-translation the viewer read in the app, so a post that looked English on TikTok imports in its source language unless the model translates it. `raw` used to be pinned "verbatim", which is what kept those lines foreign, and everything downstream reads English: unit and aisle keywords in `lib/ingredients.js`, the tag vocabulary, search. Amounts and units are explicitly *not* converted — only the wording is translated. The JSON-LD path in `extract.py` touches no model, so a foreign-language recipe site still imports in its own language; that would cost an AI call on every import to fix and hasn't been worth it.
- Planner dates go through `lib/dates.js` and stay in local time. `plan_date` is a zoneless Postgres `date`, so `toISOString()` would save an evening assignment under the previous day west of Greenwich. Weeks start Sunday.
- **An empty planner day collapses to one dashed row; a populated one keeps the card** (findings 17+18, pass 1e). The row itself is the tap target (`.planner-day-collapsed`), no button nested inside it; a day *with* meals gets a small quiet `+` in its heading instead of the old bordered Add button — same 44px reach via `.btn-icon`, a third of the visual weight. `dayEntries` is computed **after** filtering out any entry mid-undo-window, so a day whose last meal was just swiped away collapses immediately rather than waiting for the removal to actually commit.
- **Swiping a planned meal left reveals a real, always-in-DOM Remove button; dragging past a second threshold removes it outright** (finding 19, `PlannerEntry` in `components/Planner.jsx`). `.planner-entry-swipe` clips, `.planner-entry-remove` sits underneath at `right: 0`, `.planner-entry-row` is the foreground that drags — **deliberately square, no `border-radius`**, because the row carries a `transform` even at rest and a rounded `overflow: hidden` clip over two separately-composited (GPU-layered) siblings leaves a hairline seam at the corner; the plain row this replaced never had rounding either. A long press with no real drag distance snaps straight to the revealed state — the non-gesture path for anyone who can't or doesn't discover the drag. **Focusing the Remove button (Tab, or a screen reader) reveals the row exactly the way a drag does**, which is what makes it reachable by keyboard: the button is real and focusable at all times, never `display: none`, just visually parked under the row until something opens it. Only one row is ever open at once (`openEntryId` in `Planner`), and a `pointerdown` outside the open row's `[data-entry-id]` closes it — bailing while a `.sheet-backdrop` exists, same rule the pull-to-refresh listener follows. Removal itself goes through a **4.5s undo window held in `Planner`'s own state**, not App's: the entry is hidden from the list immediately, `onUnassign` only fires when the window lapses (or a second removal flushes the first one early — only one toast at a time), and leaving the Planner tab (which unmounts it) commits any pending removal immediately rather than leaving a stale timer to fire into a fresh mount later.
- **The whole week body is swipeable too** (finding 20). Both this and the row swipe share the same shape — track `startX/startY` on pointerdown, decide horizontal-vs-vertical once movement clears a slop, only `preventDefault()` after that decision so a vertical drag still scrolls the page normally — but aren't merged into one abstraction; a "reveal-or-delete" gesture and a "commit-in-one-direction" gesture are different enough that forcing them into one hook would leak. The week body's pointerdown bails immediately if the gesture started inside `.planner-entry-swipe` or any `button`/`a`/`input`, so starting a swipe on the Add-a-meal row or a day's own `+` doesn't fight that control's own tap. `weekStart` is the `key` on the days wrapper, so a week change remounts it; the `planner-week-in-left`/`-right` classes are that remount's entrance animation, not a live transition of outgoing content — "slides in the direction of travel" only asks for the incoming side to move. The nav arrows are `.btn-quiet.btn-icon` now, not `.btn-secondary` — the bordered boxes were themselves finding 20's complaint — and the week label is a real button (`onWeekChange(0)`) alongside the existing "This week" link, so tapping either returns to the current week.
- **A shopping-list source line names the recipe only, never the amount** (finding 21, `formatSource` in `lib/ingredients.js`). The merged line above it already carries the quantity in bold; repeating it per-source was reading as "300 g cherry tomatoes / Crispy Gnocchi… 300 g", half of it a duplicate. The `×N` multiplier stays — "Crispy Gnocchi ×2" is new information the merged line can't show.
- **A ticked shopping row fades as a whole rather than only recolouring its text** (finding 22, `.shopping-item-done`). `opacity: 0.55` on the `<li>`, not a lighter text colour — the earlier fix here (kept as the pattern to remember, not reverted by accident) had specifically chosen a readable grey over a low-contrast one because *the text colour was the only thing saying "done."* Opacity is different: the still-checked checkbox, unfaded in intent even though visually it fades too, is what actually carries the state, so the row can drop under the 4.5:1 text floor without losing information — the fade is reinforcement, not the sole signal. Rows never reorder on check (a moving target under a moving finger is how mistaps happen); **"Clear picked" is a client-only visibility filter, not a delete or an uncheck** — `hideDone` in `ShoppingList`, reset on every week change. It has to work this way because the list is derived, not stored (see below): there's no "hidden" state to persist, and unchecking would be a different, wrong action (it would say the item's needed again, not that it's off-screen).
- **The shopping tab's week nav + progress bar are sticky, and so is each aisle heading** (finding 23), the same `position: sticky; top: 0` treatment `.recipes-filters` uses. The progress caption became a thin bar, filled with **saffron, not the accent** — the palette rule from pass 1a: saffron is for what's simply *true* about the list (favourite star, shopping progress, a cook timer), the accent is for what you act on. **`--shopping-header-h` is a real, measured pixel value, not a guess, and getting it wrong shipped an actual bug mid-pass**: the header was first given a fixed CSS `height` matching a number that came from measuring the header *after already constraining it to that height* — circular, so it echoed back whatever was set regardless of whether the content fit. The real content overflowed by several px with no visible sign, because nothing clips it (`overflow: hidden` was never on `.shopping-header`) — the overflow just sat there until the next sticky aisle heading, painting on top of it at equal z-index because it comes later in the DOM, quietly covered it every time the list was scrolled. Two fixes, both worth keeping as the pattern: measure the header at its *natural* (`height: auto`) size before trusting a number, and keep the "Clear picked" link inside `.planner-weeklabel` next to the week range rather than in the thin bar's own row — `.btn`'s 44px floor applies to every button including `.btn-quiet`, so one riding in the same flex row as a 5px bar drags the whole row up to button height. `--shopping-header-h` is sized for the *taller* of the header's two states (with vs. without the Clear line), so the cost of being wrong is an unclaimed gap under the shorter one, never an overlap under the taller one.
- New stores mirror `lib/store.js`: a localStorage backend, a Supabase backend, one `make*Store(userId)` picker, and a one-time migrate on sign-in. `lib/plan.js` and `lib/shopping.js` follow it. Plan rows migrate *after* recipes because `meal_plan.recipe_id` is a foreign key and the recipe upload preserves local ids.
- **The shopping list is derived, not stored.** It recomputes from the week's plan every render, so it can never drift and there is no regenerate step. `shopping_items` holds only the overlay: `kind='check'` rows whose `name` is the merge key from `buildShoppingList`, and `kind='manual'` rows for hand-added items. Don't "fix" this by materialising the list — the `kind` column exists specifically so an orphaned check can't resurface as a phantom manual item after a plan change.
- **Every import path tags, including the ones with no model in them.** `infer_tags` (`app/ai.py`) is a keyword pass over the title, hashtags, description and ingredients, used three ways: it *is* the tagging for the JSON-LD path (which never calls a model and used to hard-code `tags: []`) and for link cards, and it tops up a thin model answer through `merge_tags`, which always keeps the model's own tags first. Two rules make it accurate rather than merely present: `NAME_ONLY_TAGS` may match only the dish's name, since soy sauce is not a sauce recipe and an egg in a cake is not an egg dish; and `INCIDENTAL` phrases are deleted from ingredient text first, so a vegetable soup made with chicken stock is not tagged chicken. **Diets are never inferred from absence** — a recipe that simply doesn't mention butter is not dairy-free, and that tag reaches someone avoiding it on purpose.
- **Tags are the collection mechanism** — there is no collections table, and adding one would duplicate what `tags text[]` already does. The AI may only use tags from `ALLOWED_TAGS` (`app/ai.py`, schema-enforced), mirrored in `lib/tags.js` for the editor's suggestions; **the two lists must be updated together**. Hand-typed tags are intentionally *not* restricted to that list. Filter chips come from `tagCounts(recipes)` — tags in use — never from the vocabulary, so a chip always leads somewhere.
- Search (`filterRecipes` in `lib/tags.js`) ANDs terms and does not read `instructions`. Adding a field can only widen an ANDed result set, and step text is mostly words every recipe contains, so including it would make each term match more rather than narrow better.
- Ingredient parsing (`lib/ingredients.js`) never invents detail: a line it can't parse goes to the list verbatim and merges with nothing. Same-item-different-unit stays as separate lines rather than converting, since a quiet unit-conversion error is only discovered in the shop. Aisle mapping is a keyword list matched longest-first, which is what keeps `bell pepper` in Produce and `garlic powder` out of it.
- A merged line keeps `sources` — per-recipe contributions, with a `times` count so a recipe planned twice in one week reads as `Pasta ×2 4 cups` rather than an unexplained double.
- Variant grouping (`BASE_INGREDIENTS`) is curated, not derived. Head-noun extraction would file olive oil and sesame oil together as "oil". Grouping happens **only inside one aisle**, which is what stops bell pepper and black pepper from meeting, and it never sums across variants: 2 breasts plus 4 thighs is not 6 of anything. A base needs two or more variants present before it earns a heading.
- **Style through the tokens at the top of `index.css`**, never raw values. `--fs-*` sizes are `max(rem, px)` so the rem half scales and the px floor holds legibility (mtg-web's pattern); spacing is a 4px ladder; `--line` is the decorative hairline and `--line-strong` (3.42:1) is for borders that *are* the component boundary, which is what WCAG 1.4.11 asks for. Fonts are Satoshi for UI and Clash Display for headings only, self-hosted in `public/fonts` from the same files mtg-web uses. `--fs-input` is a hard 16px: anything smaller makes iOS zoom the page on focus and never zoom back.
- **Every button is `.btn` plus one role**: `btn-primary`, `btn-secondary`, `btn-quiet`, `btn-danger`, `btn-icon`, with `btn-lg` (46px, matches a field beside it), `btn-sm` (38px, dense inline spots) and `btn-block`. **Do not write a new button rule** — the app had twenty of them for these five jobs and the merge is what made the CSS smaller. There is deliberately no outlined-accent role: one filled accent per region, everything else neutral, or "how important is this" gets answered twice on the same screen. Fields are `.field`, one rule, same reasoning. Component CSS may only adjust *layout* on a button (`flex-shrink`, `margin-left: auto`, an inherited notice ink), never its colour or height.
- **The editor writes recipes and repairs imports** (`components/RecipeEditor.jsx`, phase 9). Ingredients are one line each: **a line whose text changed is stored with `item`/`qty`/`unit` nulled**, because `readIngredient` prefers those over the raw text and stale ones would put the old ingredient on the shopping list under the new line's name. An untouched line keeps its object exactly, so fixing a title doesn't downgrade sixteen parsed ingredients. Rows carry generated keys, never their index — index keys move the caret out of the field being typed in on the first removal. Saving goes through `handleEditorSave` in `App.jsx`, which **throws** rather than swallowing the failure the way `updateRecipe` does: a star that fails can be retried by tapping again, a form that fails must keep the typing and say so.
- **The open recipe is a sheet, not an expanding card** (`components/RecipeDetail.jsx`, findings 10–16, pass 2). It used to grow the card to ~1,100px, push the other seven recipes off the bottom, and drop you somewhere else on collapse; the list keeps its scroll position now and the recipe gets the screen. `.sheet-tall` is the only thing the component adds to `Sheet` — 94dvh rather than the 85vh default, because this is a document rather than one decision, and **that rule has to live after `.sheet` in `index.css`**: same specificity, so it loses on source order otherwise and the sheet silently stays at 85vh (this shipped wrong once and only a measured height caught it). Everything the sheet holds is per-opening and deliberately unstored — ticked ingredients, step progress, a half-filled plan slot — so it clears on close; a tick left over from Tuesday's cook is worse than no tick. The component is keyed by recipe id so opening a second recipe can't inherit the first one's ticks. **Ingredients and steps are real `<input type="checkbox">` rows** (finding 11), not buttons with `aria-pressed`: "have I got the flour" is a checked state and that is the control a screen reader already describes correctly. The whole row is the `<label>`, so the target is the line and not the 22px box, and a ticked row fades wholesale exactly like a picked shopping row.
- **State and actions are separated in the detail's head** (finding 14). Favourite is a *state*, so it is a star in the head (`.detail-star`, on `--star`/`--saffron`, off `--star-off`) rather than a fourth verb in a row of three; Edit stays visible beside Add to plan; **View source and Delete live in the ⋯ overflow**. The overflow is a disclosure and deliberately **not `role="menu"`** — a real menu promises arrow-key navigation and a roving tabindex, and claiming the role for two items without implementing it is worse for a screen reader than a plain group Tab already reaches. Its trigger fires on **`pointerdown` with `stopPropagation`, never `click`**: the open menu dismisses on any outside `pointerdown` and the trigger is outside its box, so on a click handler tapping ⋯ to close would run the dismiss first and then toggle from the already-false state, reopening it — the menu could never be shut by the control that opened it. Its Escape handler is **capture-phase on `document`** so it beats `Sheet`'s bubble-phase one; without that the first Escape closed the whole recipe instead of the menu on top of it.
- **Deleting a recipe gets an undo window, not a confirm** (finding 14) — undo costs one tap and only when you were wrong, a confirm costs one every time you were right. It is held in `RecipeList`'s own state exactly the way `Planner` holds a pending meal removal: 4.5s, the recipe leaves the list (and the chip counts, and the empty-state check — everything counts off `shown`, never `recipes`) immediately, App is told nothing until the window lapses, a second delete flushes the first, and unmounting the tab commits rather than leaving a timer to fire into a fresh mount. The toast markup is the shared **`.rb-toast` / `.rb-toast-undo`**, renamed from `.planner-toast` when the second caller arrived — a `recipes-` copy of it is how the button rules got to twenty.
- **Tags are read-only in the open recipe** (finding 15) and the editor is the only place they change. Every tag used to carry a remove cross with an always-open "Add a tag" field under it, so reading a recipe put you one mistap from losing a tag. `.recipes-tag-edit`/`-remove`/`-add` still exist but belong to `RecipeEditor` alone now. `handleSetTags` is gone from `App.jsx` with them.
- **"Add to plan" is inline in the detail, never a second sheet** (finding 16) — the recipe you are planning stays on screen, and it keeps the app to one modal, the same reason "Write a recipe" swaps out of the capture sheet. It offers the **next seven days from today**, not the planner's Sunday week, because that is the question being asked; the commit button names the choice (`Add to Sunday lunch`) rather than repeating the label of the disclosure that opened it, and that disclosure drops to `.btn-secondary` while open so there is still one filled accent in the region. It goes through **`handlePlanFromRecipe`**, not `handleAssign` directly: seven days routinely reaches past Saturday, App holds only one week of plan rows, and the meal would otherwise save correctly and be invisible on a planner still showing the week you started from, which reads as the add having failed. So the planner follows the meal — **after the write resolves, never before**, since the week change is what `loadPlan` keys off and a refetch that beat the insert would replace the optimistic row with nothing. `fromISODate` in `lib/dates.js` is what turns the chosen `plan_date` back into a local Date for that; it is hand-parsed for the same reason `toISODate` is hand-formatted, because `new Date('2026-08-09')` is an ISO *instant* and lands on the 8th west of Greenwich.
- **`Sheet` takes an optional `action` for the head**, and its head is sticky. A long form's save must be reachable without scrolling to the end, and the alternative — a sticky bar across the foot — covers the fields being filled in with a full-width accent slab. The button lives outside the `<form>` and is attached with `form={id}`. The sheet has **no top padding**: it moved onto the grab handle, because padding above a sticky head is a strip content scrolls through in full view before reaching the head's background.
- **Sheets may stack, and `sheetCount` is what makes that safe.** Edit opens the editor *over* the open recipe rather than swapping it out, so cancelling returns you to the recipe you were reading. Every sheet listens on `document`, so before pass 2 both handlers ran on every key: Escape over the editor closed the editor *and* the recipe behind it (`stopPropagation` does nothing between two listeners on the same node — that needs `stopImmediatePropagation`, and even then the lower sheet's handler is registered first and would win), and Shift+Tab from the middle of the editor hit the lower sheet's trap first, saw focus outside itself and threw it to its own last item. The reference count doubles as a depth now and **only the topmost sheet handles keys**. `className` on `Sheet` is for size and nothing else; behaviour stays in the one component.
- **Everything modal is `components/Sheet.jsx`.** It owns Escape, backdrop dismiss, the focus trap, focus return to the opener, and a reference-counted body scroll lock. Don't hand-roll a second one, and don't focus the first focusable inside it — that's the head's Cancel, and a dialog that announces "Cancel" first is worse than one that announces its title. Anything listening on `document` for gestures must bail when `.sheet-backdrop` exists; the pull gesture does. **Its one effect has empty deps and must keep them** — `onClose` is read through a ref for exactly that reason. Every caller passes a fresh closure per render, so listing it as a dep meant any keystroke in a sheet tore the effect down, and the teardown's focus return pulled focus out of the field being typed into. It read as the sign-in sheet closing on the first letter.
- **Capture collapses to one FAB** (`.rb-fab`, Recipes tab only) that opens `components/CaptureSheet.jsx` (finding 1, pass 1c) — the import field, a link paste, a text paste and a from-scratch write used to be four things stacked above the list on every visit, 194px of chrome for something done a few times a week ahead of a list read every time. The three non-field routes are `.capture-route` rows with an icon, a title and a subtitle, which a bare button never had room for. The FAB floats above the tab bar rather than in the header, for the same thumb-reachability reason the tabs moved down there in pass 1b: `.rb-fab-wrap` is a fixed, full-bleed, pointer-events:none strip so it can't block taps outside its own column, with the button itself positioned at the content column's right edge inside it — the same centring trick `.rb-tabbar-row` uses inside the full-bleed `.rb-tabbar`. Tapping "Write a recipe" closes the capture sheet and opens `RecipeEditor` rather than nesting sheets. Dismissing the whole capture sheet (backdrop/Escape) leaves an in-progress paste-text draft in state rather than clearing it, since a stray backdrop tap shouldn't cost a pasted recipe; only the paste view's own Cancel clears it.
- **Search and chips are sticky, and chips are one scrolling row, not a wrap** (`.recipes-filters`, findings 4+5, pass 1d). The header above them is not itself sticky, so `.recipes-filters` sticks at `top: 0` and takes over the top edge once the header scrolls past — that's what "sticky under the header" means here, not a second sticky layer. `.recipes-chips` dropped `flex-wrap` for `overflow-x: auto` with the native scrollbar hidden; a chip cut off mid-row at the edge is the "there's more" cue, so the `allChips`/`CHIP_LIMIT`/"+N more" toggle in `RecipeList.jsx` is gone along with it — nothing needs hiding when everything is one scroll away. `tagCounts(recipes)` now renders in full, unsliced.
- **Navigation lives in the fixed bottom bar** (`components/TabBar.jsx`), and anything that has to clear it reads `--tabbar-h` rather than repeating a number. Two places do: `.rb-app`'s bottom padding, which is what stops the last recipe/day/shopping row ending up under the bar since a fixed element reserves no space, and `.rb-install`'s sticky `bottom`, which pins above the bar instead of at `0`. **The bar owns the home indicator** — `env(safe-area-inset-bottom)` is padding on the bar, and it is *added* to the page's bottom padding, never substituted for it. The bar is full-width with its buttons inside the same 640px column as the content, and it takes `--ground` with one hairline: it's the page's bottom edge, not a raised white shelf, which would just be another card. A tab is an icon over a label with no fill, outline or surface — the old top tabs used the card treatment, so three of them sat in a row above eight more of the same shape. `.rb-tab:focus-visible` sets `outline-offset: -3px` because the global ring is +2px and would draw off-screen at the bar's top edge.
- **The accent is for actions.** Buttons, a chip's on-state, focus rings. Not tab fills, not large flat areas, not section headings. On a screen whose colour should come from the food, coloured chrome is the loudest thing present and it's what dates the older recipe apps. Today on the planner follows the same rule: an inset accent rule plus a "Today" pill, not a tinted card. It is inset rather than a real left border so the day's content doesn't shift 2px against the other six.
- **A disabled outlined button takes a flat `--surface-2` fill, not `opacity`.** Fading an outline button to 40% puts its label under the contrast floor while still leaving it looking pressable. Taking the accent away and filling it grey is what actually reads as "not yet". Solid accent buttons keep `opacity: 0.6`, since there the fill is what fades.
- Notice colours come in triplets — `--warn-*`, `--ok-*`, `--info-*` — and each ink is checked against its own tint, not against `--surface`. Don't hand-mix a new pair; the five that existed before had already drifted to two different yellows carrying the same ink.
- The focus ring is one `:where(button, a, input, …):focus-visible` rule near the top of `index.css`. `:where()` keeps its specificity at zero so a component that draws its own ring still wins. Don't add per-component rings for the sake of it.
- **Recipe photos are mirrored into our own bucket** (`app/images.py`, phase 7): fetched at import while the origin's URL still works, resized to 960px and 320px, stored at `recipe-images/{user_id}/{recipe_id}-{lg,sm}.jpg` with a ~20px inline JPEG in `image_blur`. **Whether a recipe is mirrored is read off `image_url`** (`isMirrored` in `lib/images.js` looks for the bucket path) rather than stored in a flag, so the backfill can't disagree with reality. It runs in the background after the save, never inside the import, and a failure is silent and keeps the origin URL. `POST /api/recipes/image` is the one endpoint that requires a Supabase session — it keeps what it fetches, so unauthenticated it would be free storage. Uploads use the service role key and there is no insert policy on the bucket; the client only gets delete, scoped to its own folder, which is how `store.remove` cleans up.
- Mirroring writes through `store.saveImage`, an `update` of three named columns, not the `save` upsert. It lands seconds late, so the recipe it was handed may already have been starred. The mirror columns still have to be in `toRow` — every other write goes through that shape, and a column missing from it is one a favourite toggle wipes.
- **The image box never shows a gap or a broken-image icon.** `RecipeThumb` keeps a failure flag in state and renders a fallback *element*; do not "simplify" this into an `onerror` that swaps `src`, because a fallback that also fails then loops. Failure is the normal case, not the edge: Instagram and TikTok serve signed URLs that expire, plenty of origins block hotlinking with `Cross-Origin-Resource-Policy` (no client-side workaround), and an HTML error page served as 200 fires the same error event as a 404. **Every recipe image in the app goes through this component** — `size="sm"` is the row-sized variant the planner's picker uses. A new surface that reaches for a bare `<img src={recipe.image_url}>` is reintroducing a bug that was already fixed twice.
- Fallback tiles come from `lib/glyphs.jsx`. The glyph set is finite only because the AI tag vocabulary is closed, so **a new tag needs a `GLYPH_FOR` entry or it silently falls through to the monogram**. `TILE_TINTS` is a hand-checked list, not a hash into RGB. Both fallbacks share one visual treatment deliberately. **The tile is a tint of the page ground with dark ink on it, not a saturated block with a white mark** (finding 8, pass 3): the old version out-pulled every real photograph beside it, so the recipe carrying the least information looked like the most important thing in the list, and a two-column grid would have made that four times louder. Measured, since the whole treatment is a contrast question: each tint clears 13.6:1 against `--txt`, sits 1.06–1.12 off `--ground` so it still reads as a tile, and leaves `--line` 1.10–1.16 darker than the fill so the hairline is visible from inside as well as against the page. The marks are then knocked back with opacity — glyph 0.62 (4.45–4.54:1, a thin 2.6px stroke needs the headroom), monogram 0.55 (3.60–3.67:1, a solid letterform carries lower) — and **0.42 was tried and is wrong at 2.53:1, under the 3:1 non-text floor.** The hairline is an `inset` box-shadow, not a border, because the tile fills its parent's box exactly and a real border squares off against the parent's radius while the shadow is clipped by it; it is switched off on `hero`, whose left and right edges are the screen's.
- **Never put text on top of a recipe photo.** The images are arbitrary, so the worst case is near-white, and a scrim only guarantees 4.5:1 for white text from about 60% opacity — which hides the food you enlarged. Titles go under images.
- **The recipes tab is a two-column photo-led grid, not a list of cards** (finding 6, pass 3, Direction B). It was one column of bordered cards, each a 128px thumbnail beside a 195px text column — the position that costs on both counts, since the photo was too small to be worth looking at and six of eight titles still wrapped to two lines. The photo moved on top at full cell width instead: denser *and* four times the photo area, about 100px of scroll per recipe against 157px. Measured at 390×844 with 12 seeded recipes: cells are 172.5px, the first photo starts at **y=247** and **five whole cells** are above the fold. The card chrome went with it — **a surface, a border and a shadow around a photograph is three edges drawn for one object**, and the photo's own rounded corner is the cell's boundary now. The acknowledged cost is that a 172px cell holds about 34 characters a line, so `.recipes-cell-title` clamps at two lines and long titles clip; that is why the search field stays and why the detail sheet has to be good.
- The cell is a container with a stretched overlay button (`.recipes-cell-toggle`), not a button wrapping the content. A `<button>` may only hold phrasing content, so wrapping an `<h2>` and `<p>` in one is invalid and loses the heading to assistive tech. Keep `aria-haspopup="dialog"` on that overlay — not `aria-expanded`, which would promise content appearing in place rather than a sheet over the page.
- **The favourite shows on a cell but is not a control there** (`.recipes-cell-star`). Saffron in a white disc over the photo, per pass 1a's split: saffron marks what is simply *true*, the accent marks what you act on, and this is a state you can only change from the sheet's head. So it takes `pointer-events: none` and `aria-hidden`, and the fact is folded into the overlay button's own label ("Open X, favourite") instead — one control, reported in two places, rather than two controls in one cell. It never carries text; saffron is 3.77:1 inside the disc, which is the non-text floor.
- **Ruled section labels group the grid by recency, and only when they earn it** (`groupByRecency` in `lib/recipes.js`). Bands are 7 / 30 days / older, which fall out in order for free because `store.list` already sorts on `created_at` descending — no second sort, and a recipe can never appear under a heading its position contradicts. The rules are dropped entirely when a search or tag filter is on (three headings over a result of four is worse than none, and "when did I save this" is not what a search asks) **and when only one band has anything in it**, since one label over the whole list is a title for the screen, which the wordmark already is. `.recipes-rule` is **decorative, not a heading**: a heading here would sit between the wordmark's h1 and each cell's h2, forcing either an h3 demotion everywhere or a skipped level on the filtered view that has no rules at all. The `<ul>` carries the band name as `aria-label` instead, so it is announced once as "Recently saved, list, 4 items". Note the first rule replaces the grid's top margin rather than adding to it — at the full 24px it put the first photo at y=258, which is 57px of new label above the fold on the one screen this pass exists to make denser.
- **Nothing but the title and the time/servings line is on a cell face** (finding 7). Tags came off: they ran to a second row on three of eight cards and duplicated the chip rail directly above them, which is where filtering actually happens. The source host and the description excerpt came off with them. All three are in the open recipe, where the question they answer is the one being asked.
- **Long times read as hours, then as days, and dead time reads as "Overnight"** (finding 9, `formatMinutes`/`isOvernight` in `lib/recipes.js`). "720 min" and "300 min" were the two largest numbers on the screen and neither told you anything actionable. Ladder: minutes under 90, hours under a day ("1 hr 30", not "1 hr 30 min" — the second unit is what overflows a 172px cell), days beyond. **Overnight keys on dead time, never on a long total**: a five-hour braise is five hours you spend at home with the oven on, a twelve-hour focaccia is eleven and a half hours of nothing happening, so it is `total − (prep + cook) ≥ 4 hr`, falling back to `total ≥ 8 hr` only when there is no breakdown to subtract. It is capped at a day, because a seven-day sourdough starter is not "overnight" and the word would be a plain untruth — there the day count is the useful fact. `metaParts(recipe, { exact })` is the difference between the surfaces: the cell replaces the number with the word because it has one line, the sheet keeps both ("12 hr · overnight · Serves 8") because by then you want to know how long twelve hours is.
- Cell images: `aspect-ratio` reserves the box, the first `EAGER_CARDS` (4 — two grid rows, all above the fold) load eagerly at high fetch priority and the rest lazily. Don't blanket-lazy the grid — deferring the largest image in the viewport delays it rather than saving anything. Eagerness counts down the whole grid, not each section, or every band's first cells would be eager however far down the page they sat. `alt=""` throughout, since the title under it already names the dish. `RecipeThumb`'s `md` carries a **`sizes` string, not a width**, like `hero` does: a cell is `(min(100vw, 640px) − 45) / 2`, not a fixed number.
- **Offline is a read mirror (`lib/cache.js`), not a write queue.** Every successful cloud read writes a localStorage copy keyed by user (and week, where the query is week-scoped); a failed read serves that copy and sets the `offline` banner. `withMirror(key, fetch)` is the only entry point — pass a null key to skip mirroring, which is what signed-out does since localStorage is already the source. It re-throws the original error when there is no copy to fall back on. Don't make writes queue offline: replaying them later means resolving conflicts against rows another device may have changed, and the app currently promises nothing it can't keep.
- Anything that reads a week at a time must filter by that week when it renders. App holds one week's rows in state, but a week change that fails to fetch leaves the previous week's rows there, and `ShoppingList` built its list from the whole array — the shopping list for a week you had never loaded showed the last one's items. `Planner` was accidentally safe because it buckets by exact date.
- Icons come from `frontend/scripts/icons.py`; edit the script, not the PNGs. Three shapes are required and they are not interchangeable: `any` (rounded, transparent corners, shown uncropped), `maskable` (full bleed, artwork inside the 80% safe circle, cropped by the launcher), `apple-touch-icon` (opaque square — iOS masks it itself and paints transparency black). Never declare one file as `"any maskable"`.
- **The two AI endpoints stay anonymous and are capped per caller instead** (`meter_caller` in `main.py`, `usage.py`). Extraction fetches a public URL and keeps nothing, and paste must work signed out because the iOS capture path lands in Safari where the app may not be signed in — so requiring a session was rejected. The cap is 20 model calls per address per hour, counted off `ai_usage_events.ip_hash`, checked *before* any fetch or model call. The address comes from `x-real-ip` first because `x-forwarded-for` is client-settable and trusting it would let a caller mint a fresh empty bucket per request; it is stored as a salted SHA-256 (`RATE_LIMIT_SALT`, optional), never raw. **A shared secret cannot replace this** — the only caller is a public SPA, so any secret ships in the bundle.
- **Everything in `usage.py` fails open, on purpose, and the two ceilings are why that's safe.** An unreachable Supabase means neither the monthly budget nor the per-caller cap is enforced, rather than every import failing. That was reviewed and kept (audit item 27): with the per-IP cap in place an outage still leaves an endpoint no single caller can loop on, and `/api/health` reports `budget.tracked: false` so untracked never looks like healthy. Anything else designed to fail open needs the same kind of readout, or its failure and its healthy state are identical from outside.
- **`record_usage` reads the caller off a contextvar** (`_caller` in `usage.py`), set once by `meter_caller`. It sits four calls below the endpoint (main → extract → `ai._structure` → `record_usage`) and threading an argument through all four would mean every future model-call path had to remember it. A new endpoint that can reach the model must call `meter_caller`, or its spend is filed under no caller and counts toward nobody's cap.
- **`POST /api/recipes/image` checks two things, not one**: `verify_token` says who is calling, and `recipe_is_owned` (`images.py`) says the `recipe_id` in the body is a row of theirs. Without the second, an authenticated caller could post invented UUIDs and have us fetch and keep an image per call — objects `store.remove` can never reach, since it only cleans up recipes the app knows about. The ownership check **fails closed** and lives *outside* the handler's main try block, because that block ends in `except Exception` and would turn its 422 into a 502.
- Every server-side URL fetch goes through the SSRF guard in `extract.py` — never `httpx.get` a user URL directly. `fetch_html` for pages, `fetch_bytes` for images: the latter streams and aborts at the cap rather than downloading everything and measuring afterwards, which is the only safe shape at 8 MB.
- Pydantic `BaseModel` + `Field` constraints on all POST bodies; log tracebacks server-side, return opaque errors.
- CSS classes prefixed by component scope (`rb-`, `recipes-`, `planner-`); base styles before `@media` in the cascade.
- PWA share target params (`url`, `text`, `title`) are read by `readShare()` in `App.jsx` on load, then stripped from the URL with `replaceState` — that strip must never touch Supabase's auth-callback params. Don't break the query-string handling.
- iOS drops those params entirely when launching an installed home-screen app (verified 2026-08-04), so the clipboard `Paste copied link` button is the real iPhone capture path — keep it working.
- An installed PWA is **resumed, not reloaded**, so the mount-time recipe load in `App.jsx` never re-runs and a capture made in the browser stays invisible. Two things fix that and both must survive refactors: the foreground refetch (`visibilitychange`/`focus`/`pageshow`) and pull-to-refresh. Note the load effect's deps (`authReady`, `userId`, `store`) do not change on resume — `getSession()` returns a new object but `userId` is a stable string — so the effect cannot be relied on to refetch.
- The pull gesture uses native `touchmove` listeners with `{ passive: false }`, not React's `onTouchMove`, which React registers as passive so `preventDefault()` is ignored and iOS rubber-bands instead. `overscroll-behavior-y: contain` on `body` is load-bearing for the same reason. Four things about its feel are deliberate and easy to undo: the damped curve `PULL_MAX * (1 - e^(-travel / PULL_DAMP))` rather than a multiplier into a clamp (a clamp is a wall you can feel); `PULL_SLOP` before the gesture takes the touch, subtracted afterwards so nothing jumps; `dragging` tracked separately from `pull` so the indicator tracks the finger with **no** transition during the drag and animates only on release; and `PULL_MIN_SPIN`, without which a signed-out refresh finishes inside a frame and the gesture reads as having done nothing. That minimum applies to the gesture only — `refresh({ gesture: true })` — since the resume-time refresh has no audience.
- **Service worker updates run through `src/lib/pwa.js`, not the plugin's injected script.** `injectRegister: null` is deliberate: the generated `registerSW.js` binds registration to the window `load` event, which a resumed PWA never fires, so an installed app served its install-day bundle forever. `pwa.js` registers the virtual module with `immediate: true` and calls `registration.update()` on resume. Checks are gated on `setBusy()` because `registerType: 'autoUpdate'` reloads the page when a new worker claims it, and reloading mid-capture would discard the paste box.
- Signed-in state does **not** cross between Safari and the installed app: the Supabase session lives in `localStorage` and an installed PWA has its own storage sandbox. Sign in once inside the PWA. Nothing in the app can share that session, so don't treat it as a bug.
