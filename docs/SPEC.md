# Recipe Box — Spec & Roadmap

Personal recipe manager + meal planner PWA. Replaces ReciMe (paid) with a self-hosted app on the existing Vercel + Supabase free-tier setup. Decisions made 2026-08-04.

## Core decisions

| Decision | Choice | Why |
|----------|--------|-----|
| Stack | React + FastAPI on Vercel | Same shape as mtg-web; backend needed anyway (CORS blocks client-side scraping) |
| Storage | Supabase Postgres + auth | Cross-device sync, free tier, RLS pattern already proven in mtg-web |
| Social import | AI extraction from caption | oEmbed/yt-dlp pulls the caption, Haiku structures it; video transcription deferred |
| Discovery feed | Deferred past v1 | Legally/technically fuzzy; capture + planning is the real value |

## Extraction pipeline

1. **Recipe websites** — fetch HTML server-side, parse `<script type="application/ld+json">` for a schema.org `Recipe` object. Covers the vast majority of recipe sites (they mark up for Google). Fallback: microdata, then readable-text + AI extraction.
2. **TikTok / Instagram** — resolve the share URL, pull the post caption (oEmbed where available, yt-dlp metadata as fallback), send caption to Claude Haiku with a structuring prompt → normalized recipe JSON. Works when the creator wrote the recipe in the caption (very common). If no recipe in caption, save as a link card with thumbnail for manual fill-in.
3. **Manual** — plain form, plus paste-anything box that runs the same Haiku structurer.

Normalized recipe shape (matches `supabase/schema.sql`):

```json
{
  "title": "", "source_url": "", "source_type": "web|tiktok|instagram|manual",
  "image_url": "", "description": "",
  "ingredients": [{"raw": "200g spaghetti", "item": "spaghetti", "qty": "200", "unit": "g"}],
  "instructions": ["step 1", "step 2"],
  "prep_min": 10, "cook_min": 20, "total_min": 30,
  "servings": "4", "tags": [], "favorite": false
}
```

Ingredients keep the `raw` string always; parsed qty/unit/item are best-effort (needed later for shopping-list aggregation).

## Capture UX (the whole point)

- **PWA share target** — installed app appears in the OS share sheet; sharing from the TikTok/IG app lands directly in the import flow. Manifest `share_target` is configured (GET params: `url`, `text`, `title`). **Android only.**
- **iOS capture (tested 2026-08-04):** iOS has no Web Share Target support, and the Shortcuts workaround also fails: the shortcut builds a correct `/?text=<link>` URL, but when the app is installed to the home screen iOS launches it at `start_url` and discards the query string. Both halves were verified correct in isolation, so this is an iOS routing behavior with no client-side fix. The working path on iPhone is **Copy link in the IG/TikTok share sheet, then "Paste copied link"** in the app (`navigator.clipboard.readText`). Shares that arrive with no link now show a visible notice instead of failing silently.
- Paste a URL on the Recipes tab → import.
- Everything imports as editable — extraction is a head start, not gospel.

## v1 scope (user-confirmed)

Saving/importing recipes, weekly meal planner, shopping list, search/tags/collections. Discovery feed deferred.

## Phases

- **Phase 1 — Capture core (scaffolded):** FastAPI extract endpoint (JSON-LD), React shell with import bar + recipe list/detail, localStorage persistence, PWA manifest + share target wiring.
- **Phase 2 — Supabase (code done 2026-08-04):** schema from `supabase/schema.sql`, magic-link auth (mtg-web pattern, `components/Account.jsx`), one-time localStorage → cloud upload on sign-in (`lib/store.js`). Dedicated Supabase project, separate from mtg-web. App runs local-only until the env vars are set.
- **Phase 3 — Social import (built 2026-08-05):** caption fetch + Haiku structuring (`app/ai.py`, `app/social.py`), link-card fallback, paste-anything box (`POST /api/recipes/structure`), and an AI fallback for web pages with no JSON-LD. Model `claude-haiku-4-5` ($1/$5 per Mtok) with **structured outputs** — the response is schema-constrained, so there is no fence-stripping or best-effort JSON parsing. Monthly budget cap in `app/usage.py` (Supabase `ai_usage_events`, fails open when unconfigured). **yt-dlp fallback skipped:** TikTok oEmbed plus og: tags cover the caption, and yt-dlp is heavy on serverless while facing the same datacenter-IP blocks. Revisit only if captions stop arriving.
- **Phase 4a — Planner (built 2026-08-05):** week view starting Sunday (the week's shopping happens on the weekend, so a plan and the list it feeds cover the same span), assign a recipe to a day and slot through a bottom-sheet picker, remove entries, navigate weeks. Storage mirrors recipes exactly: `lib/plan.js` over localStorage signed out and the `meal_plan` table signed in, with a one-time upload on sign-in that must run *after* the recipe upload, since `recipe_id` is a foreign key. Dates are handled in local time throughout (`lib/dates.js`) because `plan_date` is a zoneless Postgres `date` and `toISOString()` would shift evening assignments a day back.
- **Phase 4b — Shopping list (built 2026-08-05):** the week's planned recipes merged into a checklist grouped by aisle. **The list is derived, never stored** — it recomputes from the plan on every render, so editing the plan updates it with no regenerate step. Only what cannot be derived is persisted in `shopping_items`: which lines are ticked (`kind='check'`, `name` holds the merge key) and hand-added items (`kind='manual'`). That `kind` column is new; re-run `supabase/schema.sql`. Parsing lives in `lib/ingredients.js` and handles mixed numbers, vulgar fractions, ranges, unit aliases and trailing prep notes, falling back to the verbatim line when it can't. Two deliberate limits: different units for the same item stay separate lines rather than being converted, and aisle mapping is a hand-written keyword list matched longest-first, so it will misfile things occasionally.
- **Phase 5a — Organization (built 2026-08-05):** search, tags, favorites. **Collections are tags, not a separate entity** — a "collection" is a saved tag filter, so there is no new table and nothing to keep in sync. Search (`lib/tags.js`) ANDs terms across title, description, tags, ingredient lines and source hostname; instructions are excluded on purpose, since with AND semantics a field full of "heat"/"stir"/"minutes" makes each typed term less discriminating. AI-suggested tags come from a **closed vocabulary** enforced as a JSON-schema `enum` in `app/ai.py` (`enum` is inside the structured-outputs subset), mirrored in `lib/tags.js` for the editor's suggestion list. Hand-typed tags are deliberately unrestricted — the vocabulary exists to stop the model inventing forty one-off tags, not to police the user. Filter chips are built from tags actually in use, never from the vocabulary. The recipes tab moved out of `App.jsx` into `components/RecipeList.jsx`; favorite and tag writes go through the existing `store.save` upsert, so no schema change was needed (`tags` and `favorite` have been on the table since Phase 2).
- **Phase 5b — Polish (built 2026-08-05):** offline caching, icon set, install prompt.
  - **Offline** is a *read mirror* of the cloud, not workbox caching of the Supabase REST calls: those URLs carry auth and filter params, and the service worker cannot tell a list read from a write. `lib/cache.js` writes every successful cloud read to localStorage keyed by user (and by week for the plan and the shopping overlay), and a read that fails serves the copy instead, with a banner saying so. Recipe photos get a workbox `CacheFirst` rule so an offline list isn't a page of broken images. Writes made offline still fail and roll back, deliberately: replaying them later against rows another device may have changed means resolving conflicts, and quietly getting that wrong is worse than saying the change didn't save. The banner clears itself on the `online` event.
  - **Icons** are generated by `frontend/scripts/icons.py` (Pillow) in three shapes, because one file cannot be all of them: `purpose: any` (rounded, transparent corners, shown uncropped), `purpose: maskable` (full bleed, wordmark inside the 80% safe circle, cropped to the launcher's shape), and `apple-touch-icon` (opaque square, iOS applies its own squircle and paints transparency black). Declaring one file `"any maskable"` is the usual mistake and looks wrong in both places.
  - **Install prompt** takes the two shapes the platforms allow: `beforeinstallprompt` with an Install button on Android, and instructions pointing at the share sheet on iOS, which has no such event. Held back until the box has at least one recipe, and dismissal persists.
  - Fixed alongside: the shopping list built from the whole plan array rather than the displayed week, so a week change that failed to fetch showed the previous week's items. Planner never showed it because it buckets entries by exact date.

- **Phase 6a — Visual overhaul, recipes tab (built 2026-08-06):** the brief was "a pleasant visual box for the food image", and the audit that came out of it found nine other things. Decisions were taken off a rendered mockup comparison rather than described in prose.
  - **Image box: 128px at 4:3, leading.** The old 64×64 was a dense-list-row thumbnail doing a browsing screen's job. 4:3 because that's the shape most food photography is framed in, so the crop takes less away than a square. `aspect-ratio` reserves the space, `align-items: flex-start` keeps the ratio fixed so the crop can't drift with title length — an inconsistent crop across rows is what makes an image list hard to scan.
  - **Never a gap and never a broken-image icon.** `RecipeThumb` holds a failure flag and renders a fallback *element* rather than swapping the `src`, which cannot loop. Fallback is a solid tile coloured from the title, carrying a line glyph when a tag maps to one and the title's first letter otherwise (`lib/glyphs.jsx`). Both share one treatment on purpose: a pale glyph beside a saturated monogram reads as two unrelated systems.
  - **Title never sits on the photo.** Ruled out on arithmetic: for white text to clear 4.5:1 over a worst-case near-white image, the scrim has to reach 60% opacity (4.77:1 at 0.60, 4.02:1 at 0.55), and 60% black over the food defeats the point of enlarging it.
  - **Card markup fixed.** The head was a `<button>` wrapping a `<div>`, an `<h2>` and two `<p>` — an invalid content model that cost screen readers the heading. Now a container with a stretched overlay button carrying `aria-expanded`/`aria-controls`, so the row stays one tap target and the heading survives.
  - **Metadata is time, then servings, then source.** Every app surveyed leads with time and none shows an ingredient count. A two-line description excerpt appears only on cards with no photo, where the row needs something to say.
  - **Favourite moved off the card face** into the open recipe. None of the six closest apps marks favourites per row; they rely on a saved filter, which the Favorites chip already is.
  - **Token layer**, adapted from mtg-web: `--fs-*` sizes carrying px floors, spacing on a 4px ladder, radius, z-index tiers, and warmed neutrals (`--ground: #f0ede6`) so a white card sits on something instead of vanishing at 1.02:1. Satoshi and Clash Display are self-hosted from the same files mtg-web uses, 91 KB precached. Contrast failures fixed: star states, chip counts, field and chip borders. Accent is actions-only now, so the active tab is a 2px rule rather than a green slab.
  - Evidence worth keeping in mind: NN/g eye-tracking measured 18% of viewing time on photos against 82% on text, so a bigger photo is a taste call, not a scanning win. What's research-backed is that images help when items are visually differentiated, which recipes are.
- **Phase 6b — Visual overhaul, the rest (built 2026-08-06):** planner, shopping list, account panel, import bar, empty states. These had inherited the fonts and the ground from 6a but were still drawing their own colours, so the app read as two apps. Roughly sixty hard-coded values are gone; the only literal colour left outside `:root` is `#fff` on an accent-filled button.
  - **Contrast, which is where most of the damage was.** `#999` on the merged-line sources (2.85:1) and `#aaa` on a ticked shopping row (2.32:1) were both failing in the one place the app gets used under bad lighting, standing in a shop. Also fixed: `#777` day dates (4.48:1, under by a hair), `#7a8a80` slot labels (3.6:1) and every field and chip border, which sat between 1.36:1 and 2:1 where WCAG 1.4.11 asks for 3:1 from a border that *is* the control.
  - **Today is a rule and a label, not a tinted card.** A green fill across a whole day is the same full-bleed chrome the tabs gave up in 6a, and seven cards deep in a scroll it was the loudest thing on screen. Now an inset 3px accent rule (inset so content doesn't shift 2px against the other six days) plus a "Today" pill, which also gives assistive tech the word — the rule alone is decoration nothing can read.
  - **The picker list uses `RecipeThumb`.** It was a bare `<img>`, so it had exactly the failure modes the component was written for: expired Instagram URLs showing the browser's broken-image icon, and no tile at all for a recipe with no photo, which left the rows ragged. Added a `size="sm"` variant rather than a second component.
  - **Empty states are places, not stray grey sentences.** Surface, radius and a dashed outline that says "this fills in", with a Clash Display lead line naming the situation and body text saying what to do. Four call sites share the one treatment.
  - **Shopping items sit on cards** like the planner's days do; on bare `--ground` a column of hairline-separated rows read as an unfinished screen next to the other two tabs. Aisle headings lost the accent at the same time — a heading is not an action.
  - **One focus ring for the whole app**, via `:where(...)` so its zero specificity lets the few components that draw their own still win. Before this, keyboard focus vanished the moment it left the recipes tab.
  - Notice colours are three token triplets (`--warn-*`, `--ok-*`, `--info-*`) rather than five hand-mixed pairs that had already drifted apart. The sheet moved to the `--z-sheet` tier from a bare `z-index: 20`, which the sticky install prompt could have covered.
  - Disabled outlined buttons take a flat inert fill instead of `opacity: 0.4`: dropping a button to 40% puts its label under the contrast floor and still leaves it looking like a button.
- **Phase 6c — Components and interactions (built 2026-08-06):** 6a and 6b tokenised the *values* in every rule but never merged the *rules*, so the app had about twenty button treatments for five jobs, each correctly coloured in its own private way. This is the consolidation, plus the account rework and the pull gesture.
  - **Five button roles, not twenty:** primary, secondary, quiet, danger, icon, with `lg`/`sm`/`block` modifiers. Deliberately **no outlined-accent role** — it existed for the paste buttons and the planner's Add, and two outline weights meant "how important is this" got answered twice per screen. One filled accent per region, everything else neutral. Heights collapsed from eight ad-hoc values (30/34/36/38/40/44/46/52px) to 38/44/46. Fields got the same treatment: one `.field`, six near-identical rules gone. Despite adding a button system, a sheet and a whole account screen, the CSS bundle **shrank from 21.9 kB to 19.8 kB**.
  - **The account left the header.** It was an address truncated to 40vw beside a "Set password" button that relabelled itself "Close" and a "Sign out" of equal weight, with a 320px form dropping out of the title bar and status messages landing right-aligned in it. Now the header holds one 40px control — the address's initial on accent when signed in, a person glyph when not — and everything else is a sheet: full-width address with no truncation, what syncing actually means, password management with the reason it exists (an emailed link opens in Safari and can never reach the installed app), then Sign out. The auth form moved into the same sheet with visible labels, a proper segmented control in a recessed track, and one primary action.
  - **`components/Sheet.jsx`** — the picker's inline modal behaviour became a component, because two hand-written copies of focus handling is how one of them ends up subtly broken. It guarantees Escape, backdrop dismiss, **a focus trap** (the picker had none, so Tab walked into the page behind an `aria-modal` dialog), focus return to the opener, a body scroll lock that is reference counted, and `overscroll-behavior: contain` so a flick inside it isn't handed to the document. Focus lands on the labelled dialog itself rather than the first focusable, which was the head's Cancel — a sign-in dialog that announces "Cancel" first.
  - **Pull-to-refresh reworked.** The indicator now follows `MAX * (1 - e^(-travel / DAMP))`: initial slope 1.02 so the first pixels track the finger exactly, stiffening as it goes, asymptotic to 90px so there is no wall. The old version moved at a flat 0.5 and stopped dead at 110px. An 8px slop means a stray pixel of downward movement no longer commits to a pull, and it is subtracted after capture so nothing jumps. `dragging` is tracked separately from `pull` so the indicator can track the finger exactly during the drag and *animate* to rest on release. The ring sweeps 0–270° and scales with progress, so arming is something you watch arrive rather than read. **A minimum 550ms spin** was the real fix for "nothing happened": signed out the store is localStorage, so a refresh finished inside a frame and the indicator flashed out of existence. Applied only to the gesture, since nobody watches the resume-time refresh. The gesture also now bails when a sheet is open and when a second finger lands.
  - `aria-current="page"` on the active tab, which previously existed only as a visual state.
- **Phase 7 — Keep the thumbnail (built 2026-08-06):** a saved recipe should never lose its picture. The thumbnail used to be whatever URL the source served, so Instagram and TikTok recipes went blank when their signed CDN URLs expired, and any origin could turn on hotlink blocking via `Cross-Origin-Resource-Policy` with no client-side answer. `RecipeThumb`'s fallback tile meant that degraded instead of breaking, which is why it was never urgent, but the photo was still gone. Now the backend fetches the image while its URL still works, resizes it and stores it in a Supabase Storage bucket, and the recipe keeps that URL. **Signed in only** — signed out there is no bucket to write to and no account to file the objects under.
  - **Mirroring runs after the save, not inside the import.** It adds a download, a decode, two resizes and two uploads, and making the capture flow wait on all of that to show a recipe whose photo is already on screen would be paying at the one moment the app is being watched. `POST /api/recipes/image` is called in the background from `App.jsx` and patches the row when it lands. A lazy "mirror on first view" was the other option and is worse: by the time an Instagram URL is looked at, it may already be the expired URL this exists to replace.
  - **The endpoint asks who is calling; the other two don't.** Extraction is anonymous because it fetches a public URL and keeps nothing. This one writes bytes into our bucket and keeps them, so it is free hosting for anyone who finds the API. `app/auth.py` verifies the caller's Supabase access token against GoTrue and the objects land at `recipe-images/{user_id}/{recipe_id}-{lg,sm}.jpg`. Verification is a round trip rather than a local signature check: the JWT secret would be a fourth env var, new Supabase projects sign asymmetrically, and a token belonging to a deleted user still validates locally. ~100ms on a request about to spend a second downloading a photo.
  - **Two widths and an inline blur.** 960px is the copy of record and 320px is what the card actually renders — `srcset` with `sizes` set to the real box width, so a 128px tile on a 2x phone stops pulling a 3000px hero. Measured on a 1 MB Unsplash photo: 133 kB and 18 kB out. The third output is a ~20px JPEG inlined as a data URI in `image_blur`, so the reserved image box holds a blurred version of the photo that is coming rather than a flat tint. No CSS filter on it; a 20px image scaled to 128 is already soft, and a filter on the element that clips the photo costs a layer.
  - **Ownership is read off the URL, never stored in a flag.** `isMirrored` looks for the bucket path in `image_url`. A flag can disagree with the column beside it after a half-finished mirror or a restored backup, and then the backfill either skips a recipe that still needs doing or redoes one that doesn't. The URL cannot be wrong about where it points.
  - **The backfill is the same function as the import path**, run over the list on every load, two at a time. A recipe saved last week and one saved ten seconds ago are the same problem. It was worth running even for recipes whose URLs have already expired: those fail, cost one request each, and the failure is indistinguishable from what the app already shows. Attempts are remembered per session so a dead URL isn't rediscovered on every resume, and a reload is the retry. Nothing is attempted while offline, so a tunnel doesn't burn the attempt.
  - **A failed mirror is silent and keeps the origin URL.** That is exactly the state the recipe was in before phase 7, and `RecipeThumb` already handles that URL dying. Telling someone their photo didn't get backed up asks them to do something about it when there is nothing they can do.
  - **The mirror writes three named columns, not a whole row.** `store.saveImage` is an `update`, not the `save` upsert: mirroring lands seconds after a recipe appears, and the row it was handed is stale if the recipe was starred in the meantime. The same care in reverse is why `image_thumb_url` and `image_blur` had to go into `toRow` — every write goes through that shape, so a column missing from it is a column a favourite toggle wipes.
  - **Delete cleanup is client-side, via a Storage policy.** Storage has no foreign keys, so a deleted recipe leaves two objects nothing will ever read or remove, and on a free tier that is a quota filling up for no reason. The bucket has one policy, `for delete to authenticated` scoped by `(storage.foldername(name))[1] = auth.uid()::text`. There is deliberately no insert policy: uploads come from the backend with the service role key, which bypasses RLS, so the client cannot write here at all. The bucket is public-read because these are `<img>` sources — a signed URL would expire and put us back where we started, and the service worker's `CacheFirst` rule can only keep a plain one. The path is two UUIDs.
  - **`fetch_bytes` streams and cuts off at the cap**, which `fetch_html` does not do — it reads the whole body and checks the length afterwards. That is fine against a 3 MB HTML cap and not fine at 8 MB of image, where a hostile or merely broken origin can send bytes for as long as we keep reading. Pillow is the thing that decides whether what arrived is a photo, which is also how a hotlink-block page served as `200 text/html` gets caught. Decompression bombs are rejected off the header, before any pixels decode.

## Security notes

- `extract` endpoint fetches arbitrary user-supplied URLs → SSRF guard (public IPs only, http/https only, size cap, timeout) lives in `backend/app/extract.py`. Keep it on every new fetch path.
- Caption text is untrusted input to the AI structurer — wrap in `<user_input>` tags, injection defense in system prompt (vault-level rule).
- Pydantic models with Field constraints on all POST bodies; opaque client errors.

## Non-goals (for now)

Multi-user sharing/households, nutrition data, recipe scaling, discovery feed, native apps.
